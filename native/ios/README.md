# Native iPhone and Apple Watch App

A read-only companion for a Token Monitor Hub: an iPhone app (Overview, Limits, Devices and Settings tabs, plus a Status tab that is hidden by default), Home Screen and Lock Screen widgets (Usage, AI Tool Limits and Activity), a watchOS app, and watch complications. A phone has no local AI-tool logs, so every surface reads the Hub's HTTP API ([Hub reads](#hub-reads) lists the endpoints; the wire format is in [docs/API.md](../../docs/API.md)) and nothing is ever written to the Hub: every request is a `GET`. The secret is sent as `Authorization: Bearer`, never as `?secret=`.

## Connecting to a Hub

Any Hub from the [Multi-device sync](../../README.md#multi-device-sync) section (Options A to C; iCloud Drive is not a Hub) works, as long as the phone can reach it:

- **Host hub on this device** (the desktop widget): the phone must be on the same network or tailnet. Enter one of the addresses the widget lists and its secret. The Hub runs only while Token Monitor is running.
- **Node hub** (`npm run hub`, port 17321) on an always-on machine: same network or tailnet.
- **Cloudflare Worker**: an `https://` address that works from anywhere, including mobile data.
- **Tailscale**: reaches the first two from outside the home network with the phone's Tailscale app running.

Addresses without a `scheme://` get `http://` when the host is on the local network or a tailnet (loopback, `.local`, `.home.arpa`, unqualified names, RFC 1918, link-local and `100.64.0.0/10` addresses, IPv6 ULA, and Tailscale `*.ts.net` names) and `https://` for everything else, because the Node hub and the Host hub serve plain HTTP and an `https://` guess would only fail the TLS handshake. An explicit scheme is always kept, so a Tailscale Serve or Funnel HTTPS address must be typed with `https://`. A pasted `/api/...` path, query and URL credentials are dropped; a reverse-proxy path prefix is kept.

Plain `http://` to a host that is not local or on a tailnet is allowed but shows a warning in the connection form, because the secret and usage would cross the internet unencrypted. The first request to a LAN Hub makes iOS ask for Local Network access (`NSLocalNetworkUsageDescription` on the iPhone app); if it was declined, the app reports the Hub as unreachable and points to Settings › Privacy & Security › Local Network.

## Requirements

- Xcode 16 or newer: the project uses file-system synchronized groups (`objectVersion 77`). It was created with Xcode 26, and CI builds with the Xcode on GitHub's `macos-latest` image without pinning one.
- iOS 17 and watchOS 10 deployment targets. The iPhone target also builds for iPad, but only an iPhone pairs with the watch.
- Swift language mode 5 everywhere (`SWIFT_VERSION = 5.0`, package tools 5.9): strict concurrency checking would turn the shared Foundation types into build breaks. No third-party dependencies.
- An Apple Developer team to run on a device (see Configuration). Unsigned builds, as in CI, need none.

## Configuration

`Config/Base.xcconfig` holds committed, non-personal placeholders and ends with `#include? "Local.xcconfig"`; both project-level build configurations are based on it, so every target inherits it. Personal values go in `Config/Local.xcconfig`, which is gitignored:

```bash
cp native/ios/Config/Local.xcconfig.example native/ios/Config/Local.xcconfig
# then set TM_BUNDLE_ID, TM_APP_GROUP and DEVELOPMENT_TEAM in it
```

The placeholders (`com.example.tokenmonitor.mobile`, `group.com.example.tokenmonitor`, empty team) build unsigned, which is what CI does. Only the iPhone app's bundle id is configurable; the others are derived from it because an embedded bundle's id must be prefixed by its host's and the watch app's `WKCompanionAppBundleIdentifier` must equal it:

| Scheme and target | Folder | Bundle id |
|---|---|---|
| `TokenMonitor` (iPhone app; embeds the widget and the watch app) | `TokenMonitor/` | `$(TM_BUNDLE_ID)` |
| `TokenMonitorWidget` (Home and Lock Screen widgets) | `TokenMonitorWidget/` | `$(TM_BUNDLE_ID).widget` |
| `TokenMonitorWatch` (watch app; embeds the complications; needs the iPhone app) | `TokenMonitorWatch/` | `$(TM_BUNDLE_ID).watchkitapp` |
| `TokenMonitorWatchWidget` (complications) | `TokenMonitorWatchWidget/` | `$(TM_BUNDLE_ID).watchkitapp.widget` |

`TM_APP_GROUP` must start with `group.`, exist in the Apple Developer account of `DEVELOPMENT_TEAM`, and be enabled for all four App IDs above. The same identifier is the App Group entitlement and `TMAppGroup` Info.plist key of every target, the `UserDefaults` suite and container that hold the Hub URL and the snapshot, and the Keychain access group of the Hub secret (valid on iOS and watchOS without a `keychain-access-groups` entitlement). Changing `TM_APP_GROUP` therefore starts from an empty state. Where the App Group container is unavailable the app keeps working on its own caches directory and standard defaults, but widgets and the watch see nothing of its data, so exercise them with a build signed by your team.

Do not pick the team in Xcode's Signing & Capabilities tab, and do not set the bundle id or App Group in a target's build settings. Xcode writes the team into `project.pbxproj`, where it shadows `Local.xcconfig` and puts personal values in the diff.

## Build and test

```bash
swift test --package-path native/ios/TokenMonitorKit
xcodebuild -project native/ios/TokenMonitor.xcodeproj -scheme TokenMonitor -destination 'generic/platform=iOS Simulator' build CODE_SIGNING_ALLOWED=NO
xcodebuild -project native/ios/TokenMonitor.xcodeproj -scheme TokenMonitorWatch -destination 'generic/platform=watchOS Simulator' build CODE_SIGNING_ALLOWED=NO
xcodebuild -project native/ios/TokenMonitor.xcodeproj -scheme TokenMonitorWatch -destination 'generic/platform=watchOS' build CODE_SIGNING_ALLOWED=NO
```

These are the steps of the `ios` job in `.github/workflows/ci.yml`. The package tests (XCTest) cover the Foundation-only core and are kept runnable on Linux; CI runs them on macOS. SwiftUI code (`TokenMonitorUI` and the app, widget, watch and complication targets) compiles only on Apple platforms, so the CI `xcodebuild` steps and Xcode are its only build. There are no Xcode test targets, and `npm run verify` does not cover the Swift code; its only Swift-adjacent check is `tests/shared/iosVendorCatalog.test.js` (generated files, see below).

Logic ported from the desktop is tested against golden outputs, not against re-derived expectations. `Tests/TokenMonitorKitTests/Fixtures/` holds the first captures (health, stats and the SSE stream), and `Fixtures/v2/` holds responses captured verbatim from a real Node Hub under a frozen clock (`capture.json`) plus `golden/`, which was rendered by running the desktop's own JavaScript modules on them; each golden's `source` field names the module, function and arguments, and `Fixtures/v2/README.txt` describes every file. `Fixture.data()` reads only `Fixtures/`, so tests of `Fixtures/v2` use their own loader. The Swift tests compare with the committed files and never run Node, so changing a ported desktop module fails nothing by itself: re-render the golden and update the Swift port together. The script that captured the fixtures and rendered the goldens is not part of the repository. `Fixtures/v2/.gitattributes` keeps the export CSVs' CRLF line endings and the SSE capture's final blank line byte-exact; keep it when moving files.

In Xcode, open `native/ios/TokenMonitor.xcodeproj` and run the `TokenMonitor` scheme on an iPhone or simulator, or `TokenMonitorWatch` on a watch or simulator. The widget schemes debug the extensions, and each widget file carries `#Preview(as:)` timelines that render every supported family in the canvas.

The vendor marks and `VendorCatalog+Generated.swift` are generated from the desktop's tables (see [Compatibility surfaces and gotchas](#compatibility-surfaces-and-gotchas)): `npm run sync:ios-vendors` rewrites them and `npm run sync:ios-vendors -- --check` exits 1 when any is stale.

## Architecture

`TokenMonitorKit` (a local Swift package, `native/ios/TokenMonitorKit`) has two products:

- **`TokenMonitorKit`** is Foundation-only and must keep building and testing on Linux: the Hub client and lenient wire models, preferences, number and money formatting, the presentation logic ported from the desktop (Limits, sessions, devices, projects, subscriptions, History, heatmap, trends, fixed ranges, model aliases, export), the snapshot types and the vendor catalog. `Security` and `FoundationNetworking` are imported behind `canImport`, and the SSE stream (`statsStream()`) exists only on Darwin. Decoding is lenient, so an unknown or missing field never fails a whole response. It returns enums, numbers and structured labels, never user-facing text.
- **`TokenMonitorUI`** is shared SwiftUI (theme, meters, vendor marks, the Activity heatmap, trend charts, session views, accessory views) for the app, widgets and watch. Every file is wrapped in `#if canImport(SwiftUI)` and takes text as parameters, so localization stays in each target's catalog. The user's presentation choices reach it through `.tmPresentation(_:)` and `@Environment(\.tmFormatter)`.

Display logic lives in the Kit so it is testable on Linux and identical on every surface. Targets format numbers and costs through `PresentationContext.formatter` (`DisplayFormatter`), which applies the user's units, currency and rates; the original `TokenFormat` helpers ignore them and are not used for display.

### Hub reads

All requests are `GET` with `Accept: application/json`, except the SSE stream. Everything but `/api/health`, which is public, carries `Authorization: Bearer`.

| Endpoint | Read by | When |
|---|---|---|
| `/api/health` | app | connection test and the Hub screen (runtime, `hubBuild` revisions) |
| `/api/stats` | every surface | the totals everything is built from; the app decodes with `.app`, extensions with `.compact` (see [Decoding and the snapshot](#decoding-and-the-snapshot)) |
| `/api/stats/stream` (SSE) | app | Live refresh mode only, while the app is active |
| `/api/history` | app | lazily, when a screen needs it (Activity, Trends, stat cards, WEEK/7D/30D, export); then only when the stats' `historyRevision` moves |
| `/api/devices` | app | per-device History records (a scoped device's Activity and Trends, the device screens), when `deviceHistoryRevision` moves |
| `/api/subscriptions` | app | when the stats' `subscriptionsUpdatedAt` moves |
| `/api/sync/settings/modelAliases` | app, watch app, complications | when the stats' `syncSettingsRevisions.modelAliases` moves; widgets only read the cached copy |
| `/api/sync/settings/customPricing`, `/api/sync/content` | app | on demand, for the Hub screen |

A Hub that predates an endpoint answers 404 or 405; the app then does without it. For History it falls back to the 30-day preview inside `/api/stats` (no per-tool or per-model stacking, no fixed ranges) and does not ask again until the connection changes or History is refreshed by hand.

Besides the Hub, the app contacts only public services, with plain `GET`s that carry nothing about the Hub, the user or their usage. The exchange rates come from the same free CDN the desktop uses (`cdn.jsdelivr.net`, falling back to `latest.currency-api.pages.dev`); only the app fetches them, at most daily, and the watch receives the cache from the phone. The Status tab reads the vendors' public Statuspage JSON directly, never through the Hub: `status.claude.com`, `status.openai.com`, `status.cursor.com` and `deepseek.statuspage.io` (DeepSeek's own page serves HTML only). Those requests use an ephemeral session without cookies or a URL cache and set only `Accept` and a `User-Agent` of the form `TokenMonitor/<version> (+https://github.com/Javis603/token-monitor)`, the desktop's. Widgets, the watch and complications contact only the Hub.

### Display preferences

`DisplayPreferences` is the one settings object. It is stored as JSON in the App Group's `UserDefaults` under `displayPreferences.v1` (`PreferencesStore`), written by the app only through `AppModel.updatePreferences(_:)`, read by widgets and complications through `PresentationContext.load()`, and sent to the watch as a `PreferencesPayload` (see [iPhone to watch](#iphone-to-watch)). Property names are the desktop's settings keys wherever the desktop has the setting; `deviceScope`, `appRefreshSeconds`, `widgetRefreshMinutes`, `watchRefreshSeconds`, `complicationRefreshMinutes` and `showStatusTab` are iOS-only. Decoding is lenient per key: a missing, mistyped or out-of-set value takes that key's default, unknown keys are ignored, and only a top level that is not a JSON object fails. Every save normalizes (id lists are trimmed, lowercased, de-duplicated and capped at 64, the Overview module order always lists every module once, and so on), so equal settings encode to equal bytes.

Units, currency and manual exchange rates, vendor colours, tool icons, used or remaining, the device scope, tool order, hiding and pinning, the Limits provider order and hidden Limits items, and the hidden Home providers reach the widgets, the watch app and the complications that draw them. The Activity metric and active-days window also reach the Activity widget. Settings that only shape app screens (Overview modules and their options, the period menu, the live rate, sessions, Limits display options, the Status tab, the app's refresh mode) stay in the app: `AppModel.sharedPart(_:)` lists them, and a change to one costs the widgets and the watch neither a reload nor a push.

**Refresh settings.** Settings › Data › Refresh intervals has a control for each of the app, the widgets, the watch app and the complications, and the Status tab's re-check interval lives in Settings › Status › Status options. The choices and the timings derived from them are in `RefreshPolicy`; every default reproduces the fixed timings the first version used.

| Setting | Choices | Effect |
|---|---|---|
| `appRefreshSeconds` | Live (default), 1, 2, 5, 15, 30 minutes | Live holds the SSE stream (with the backoff, polling fallback and 8 s grace described below). An interval closes the stream and reads `/api/stats` every N seconds while the app is active; numbers younger than the interval are not read again at once when the app comes back, and the live token rate is hidden. Pull to refresh always works. |
| `widgetRefreshMinutes` | 15 (default), 30, 60 minutes | A cached snapshot built for the current settings and younger than `max(5, N − 5)` minutes is shown as is, the next reload is requested after N minutes, and data is stale after 2N. The 15-minute default gives 10 / 15 / 30. |
| `watchRefreshSeconds` | 1 (default), 2, 5, 15 minutes | The watch app polls every N while on screen and skips a re-activation fetch younger than `min(30 s, N / 2)`; numbers are stale after `max(15 min, 2N)`. |
| `complicationRefreshMinutes` | 20 (default), 30, 60 minutes | A cache older than N minutes, or built for other settings, costs one Hub request; the reload is requested after N (60 while no Hub is configured), stale after `max(60 min, 2N)`. |
| `serviceStatusRefreshMs` | Manual, 1 (default), 2, 5, 15, 30 minutes | The Status tab re-checks at this interval while it is visible; the client caches a result for 60 s, a failure for 10 s. |

The widget and complication intervals are requests: WidgetKit budgets reloads, so a widget can lag well behind them.

**Device scope.** `deviceScope` is `all` or `device:<Hub device id>` (`DeviceScope.storageValue`). When a device is chosen, totals, cost, components, tools, models, throughput, sessions and projects come from that device's own periods in `/api/stats` (`HubStats.scoped(to:)`). The snapshot follows it too, so widgets, the watch and the complications show that device and name it, and the Activity file is written for the scope. The device's Activity, Trends, stat cards and fixed ranges come from its record in `/api/devices`, not from `/api/history`. The Hub's own aggregate rules apply, not the desktop device list's: a device's `today` or `month` window that has ended counts as zero, `allTime` never expires. Limits and the Devices tab never follow the scope (Limits are aggregated per provider account, not per device). A device the Hub no longer lists falls back to all devices everywhere, with a notice (`ScopedStats.isScopeMissing`, `SnapshotScope.isMissing`); the stored preference is kept, so the scope returns if the device does. Switching Hub resets it to all, because device ids are per Hub. The snapshot's 30-day trend is empty for a scoped device, because a device's History is not part of `/api/stats`.

### Decoding and the snapshot

`GET /api/stats` carries every session of today and this month, a project rollup per period and a full copy of each period per device. The app shows all of that; extensions have a small memory limit and show a handful of numbers. `HubDecodingOptions` (passed to `HubClient.stats(options:)`, `statsStream(options:)` and `HubStats.decode`) chooses what is built: `.app` (sessions, projects and every device's detail, used by the iPhone app), `.compact` (totals, tool and model rows and device totals only, the default and what widgets, the watch and complications use) and `.compact(scopedTo:)` (compact plus the scoped device's detail, so a device-scoped extension can show that device's periods). Session titles and project names exist only in the app: they are decoded only with `.app` and never reach a snapshot, the App Group or WatchConnectivity.

`SnapshotBuilder` is the single build path of `TokenSnapshot`, the bounded projection (top tools and models per period, a 30-day trend cap, a few limit windows per provider, masked account emails, no secret) that widgets, the watch app and complications render. The app, the widgets, the watch app and the complications all build through `SnapshotBuilder.snapshot(from:fetchedAt:hub:)` with the stored preferences and the Hub's cached alias document (`SnapshotBuilder.load(hubKey:)`), so a snapshot written by any of them is what the others would build. It folds model aliases, applies the device scope, orders, hides and pins tools before keeping the top `TokenSnapshot.maxShares` (hidden tools count as Other), orders the Limits by `limitProviderOrder` (catalog order by default; accounts of a provider keep the Hub's order) and compacts them: emails masked, path-like names dropped, only visible primary windows, at most `maxWindowsPerProvider`, no reset credits, usage summary, tranches or source device. An encoded snapshot stays under 16 KB (a test pins it).

`schemaVersion` is still 1: every field added since the first version is optional and written only when set. `scope` names the scoped device (`SnapshotScope`: id, name, stale, missing), `aliasRevision` is the alias document's revision, `projectionKey` is a stable hash of everything besides the stats that shapes the snapshot (scope, alias revision, tool order, hidden and pinned tools, Limits order and hidden Limits items), and `PeriodSummary.unpricedTokens` backs the compact "$1.23 + ?" cost. A reader whose own builder's `projectionKey` differs treats the cached snapshot as due for a refresh (`SnapshotBuilder.isCurrent(_:hubKey:)`) but may still show it as a fallback. Old readers ignore the new keys, and new readers treat an old file as all devices with no projection.

Each snapshot also records `hubKey`, the `HubConnection.snapshotKey` of the Hub it came from: a hash of the normalized URL, never derived from the secret. Every reader checks it with `belongs(to:)` or `belongs(toHubKey:)`, so after a Hub switch a snapshot of the previous Hub is treated as missing: the iPhone app stamps and pushes only its current Hub's, the watch ignores a pushed or cached one from another Hub, and widgets and complications discard a fetch whose Hub changed while it was in flight instead of showing or saving it. A snapshot without a `hubKey` (written before the field existed) is shown. The watch, widgets and complications compare against `HubConnectionStore.snapshotKey` or `HubConnection.snapshotKey(for:)`, which need only the saved URL, because the Keychain refuses the secret before the first unlock.

### Files and caches

| Data | Where | Valid for | Read by |
|---|---|---|---|
| Display preferences | App Group defaults, `displayPreferences.v1` | until changed | all (the watch keeps its own copy) |
| Exchange rates | App Group defaults, `exchangeRates.v1` | refetched when the cache is neither from today (UTC) nor under 24 hours old | app fetches; widgets read; the watch receives them |
| Hub URL | App Group defaults, `hubBaseURL` | until changed | all |
| Hub secret | Keychain, service `TokenMonitor.Hub`, account `hub-secret`, in the App Group's access group | until changed | all |
| Snapshot | App Group container, `Library/Caches/TokenMonitor/token-snapshot.json` | `hubKey` and `projectionKey` | all |
| Activity | same folder, `activity.json` | `hubKey` and device scope | app writes; the Activity widget reads |
| Model aliases | same folder, `model-aliases.json` (`{hubKey, document}`) | alias revision | app writes; widgets and complications read; the watch app and complications may refresh it |
| History, device records, subscriptions | the app's own caches folder, `TokenMonitor/HubResponses/<kind>.cache` (`HubResponseCache`) | `hubKey` and revision | app only |

The App Group container is also what the watch has, with the same file names. Where it is unavailable the app keeps working on its own caches directory and standard defaults.

**Hub switch.** Saving a different Hub URL or disconnecting drops everything read from the old Hub: the stats, aliases, live rate, the History, subscription, Hub-info and Status stores and their cache files, the Activity file, exported files and every tab's navigation stack. It also clears the snapshot (the watch and widgets are told), resets the device scope to all devices, and on disconnect removes `model-aliases.json`. Other preferences are kept. Every cache is keyed by `hubKey`, so a stale file for another Hub is never returned either.

## Surfaces

**iPhone app.** The Overview tab (the desktop's Home) has a device-scope menu, the period picker (Today, a middle segment that is This month, This week, Last 7 days or Last 30 days according to `periodMonthMode`, and All time), a headline with tokens, cost and rate, then the modules the user ordered and showed (Token components, Limits, Tools, Models, Sessions, Devices and the Activity mosaic; Tools and Devices are hidden by default, as on the desktop), and links to the Tools, Models, Projects, Sessions and Trends screens. Limits and Devices are tabs of their own. Status, the vendors' public status pages, appears only when Settings › Status › Status options › Show Status tab is on (Status options also opens from the Status screen, and the screen stays reachable from Settings while the tab is off). Settings covers the connection, display options, the Limits and Sessions options, Subscriptions (read-only), the Hub screen (runtime, `hubBuild` revisions, sync capabilities, model aliases and shared custom pricing), the refresh intervals and Data export. Week, 7D, 30D, Activity and Trends come from History and load lazily, when a screen first needs them.

Data export builds the desktop's file set (`token-monitor-export.json`, `token-monitor-snapshot.csv`, and the daily and daily-models CSVs when History has rows) from the raw `/api/stats` and `/api/history` bodies (`ExportSerializer`) for the share sheet. As on the desktop it covers every device, costs stay in USD, model ids are raw and session text is removed. The content is the desktop's but the order is not: the desktop writes objects in the wire's insertion order, which Swift dictionaries cannot keep, so on iOS nested JSON keys are sorted and CSV rows are sorted deterministically (snapshot rows by period, then tool before model, then name; the daily files by date, then name). Headers, columns, the BOM, CRLF line endings and number text match the desktop byte for byte. A Hub without `/api/history` exports the snapshot files only; any other History failure fails the export rather than writing a set that silently lacks the time series. The files are temporary and the next export, the next visit to the screen or a Hub change removes them.

While the app is active in Live mode it holds `GET /api/stats/stream` and applies every `stats` event. Active means the app's combined scene phase, read in `TokenMonitorApp` rather than in a view, so on iPad one window going to the background does not stop updates while another is still on screen. A dropped stream reconnects with capped exponential backoff and jitter; after four consecutive failed attempts it polls `/api/stats` every 30 s and retries the stream every ten polls. If a proxy buffers the stream and no event arrives within 8 s, one plain read fills the screen. In an interval mode there is no stream; it reads `/api/stats` every N seconds instead. Errors only the user can fix (bad address, wrong secret) stop updates until settings change or the user pulls to refresh. HTTP 503 reads as "The Hub is unavailable" (the Hub or a proxy in front of it is down, or a Cloudflare Worker has no `TOKEN_MONITOR_SECRET`) and keeps retrying. Going to the background closes the stream; the app does no background fetching. Changed numbers rewrite the App Group snapshot and hand it to the watch bridge at most every 20 s, writing the latest numbers when that window ends; the first numbers after launch or a connection change are written at once, and a pending write is flushed when the app goes to the background. Unchanged numbers refresh the snapshot once a minute. A snapshot write reloads widget timelines at most every 5 minutes, while saving or clearing the connection, a change to a preference the widgets read, new exchange rates and a Hub switch reload them at once. Whenever the app loads History it also writes `activity.json` for the Activity widget (see below), and reloads that widget's timelines at most every 5 minutes, except right after a scope or Hub change.

**iOS widgets.** Usage (small, medium, large, and Lock Screen circular, rectangular, inline; period and breakdown are configurable), AI Tool Limits (small, medium, Lock Screen circular and rectangular; optionally pinned to one provider) and Activity (medium and large; the heatmap's metric is tokens or cost, "App Setting" by default) all follow the device scope, units, currency, vendor colours and tool icons wherever they draw them. A timeline provider for Usage and Limits shows a cached snapshot as is when it was built for the current settings (`SnapshotBuilder.isCurrent`), was fetched today and is younger than `max(5, N − 5)` minutes for the widget refresh interval N; otherwise it makes one Hub request with a 10 s timeout, falling back to the cache. It asks WidgetKit for the next reload after N minutes and marks data as stale when it is older than 2N minutes, from an earlier day, or the Hub reports every device (or the scoped device) as stale. A period that has rolled over since the fetch (today after midnight, this month after the 1st, in the device's calendar) shows "—" instead of the old totals. Extra entries at the stale moment, at midnight and at upcoming limit resets keep countdowns from running past their reset. Concurrent loads share one fetch (`SnapshotFetchCoalescer`, keyed by the Hub, with a fetch reused for 60 s), because every widget decoding its own copy of `/api/stats` is how an extension exceeds its memory limit; a result built for settings that changed meanwhile is fetched once more. The Limits widget's automatic list drops the hidden Home providers and follows `homeLimitProviderOrder` when one is set, else `LimitProvider.sortedByUrgency` (healthy readings first, least left first). The constants are in `WidgetTiming` (`WidgetSupport.swift`) and `RefreshPolicy`.

The Activity widget never decodes History. The app writes the compact `activity.json` (`ActivitySnapshot`: one zero-filled entry per day from `startDay`, tokens and `costMicros`, already patched with live today, bounded by `maxDays` and `maxEncodedBytes`) after every History load and as live today moves (at most once a minute; unchanged data hourly), keyed by Hub and device scope. Medium shows about the last 20 weeks with their active days, and large the rolling 12 months in two rows, both Sunday-first like the desktop and with month labels; large adds a Less/More legend, the active days (in the Activity module's active-days window) and the peak day's tokens. With no file for the current Hub and scope it says to open Token Monitor to load activity, and it marks its data stale after a day, because the file is only rewritten while the app is used. Widgets link into the app with the routes below.

**Watch app.** Shows the cached snapshot first, then fetches the Hub itself every N seconds (the watch refresh interval, a minute by default) while on screen; there is no SSE, because a held connection costs more battery than a poll while the screen is on. A snapshot younger than `min(30 s, N / 2)` and built for the current settings is not refetched when the app becomes active again, and numbers older than `max(15 min, 2N)` are marked stale. It decodes `.compact(scopedTo:)`, refreshes the model-alias document when the Hub advertises a new revision, and builds through `SnapshotBuilder` from the preferences the iPhone sent, so it shows the same scope, units, currency, tool order and visible Limits items as the phone. A settings change from the phone rebuilds the snapshot at once from the last stats when they cover the new scope. As on the widgets, a period that has rolled over since the fetch shows "—" (and no tools) until the next one. A wrong secret makes it ask the iPhone to sync again.

**Complications.** Summary and Quota, in circular, rectangular, inline and corner families. They read the watch-side snapshot, make one best-effort Hub request when it is older than N minutes (the complication interval, 20 by default) or was built for other settings, and ask for a reload after N minutes (60 when no Hub is configured), plus an entry at midnight, after which Summary shows "—" until today's numbers arrive. Both complications share that request through the same `SnapshotFetchCoalescer` the iOS widgets use, instead of each decoding its own copy of `/api/stats` in a memory-tight extension, on an ephemeral session without a URL cache that gives up after 15 s. Quota leads with the tightest window (`LimitProvider.sortedByUrgency`, which is also the iOS Limits widget's automatic order while no Home provider order is set), without the hidden Home providers. A window without a meter (a balance-only account) shows its value on a plain disc, here and on the iOS widgets, never as an empty ring that would read as nothing left.

### iPhone to watch

The watch cannot read the iPhone's Keychain or App Group, so `PhoneSessionBridge` (iPhone app) sends the connection, snapshot and display preferences over WatchConnectivity and `WatchSessionBridge` (watch app) stores them in the watch's own Keychain item and App Group, which is also what the complications read. Payload keys:

| Key | Meaning |
|---|---|
| `v` | Protocol version (`protocolVersion`, currently 1) |
| `rev` | Milliseconds, strictly increasing across launches; the watch drops anything older than the connection state it already applied |
| `connected` | `false` means the user disconnected the Hub; the watch then clears its copy (connection, snapshot and model aliases) |
| `hub` | JSON-encoded `HubConnection` (URL and secret) |
| `snapshot` | `TokenSnapshot` JSON |
| `prefs` (`PreferencesPayload.contextKey`) | `PreferencesPayload` JSON, `{v: 1, preferences, rateCacheData}`: the display preferences and the phone's exchange-rate cache, so the watch converts costs with the same rates without fetching any |
| `request` = `sync` | Watch-to-phone message asking for the current state; the reply has the same shape |

`updateApplicationContext` carries the connection, snapshot and preferences: a connection or preferences change goes out at once, snapshot-only updates collapse to at most one a minute, and identical content is not resent. `prefs` also rides in the sync reply, never in a complication transfer. It is limited to 8 KB (`PreferencesPayload.defaultMaxBytes`): over that, `vendorColors` is dropped first, then `limitProviderHiddenItems`, and if it still does not fit the phone sends no preferences update. The watch stores the preferences and rates, rebuilds its snapshot when the projection changed and reloads the complications at once. `transferCurrentComplicationUserInfo` carries only `v`, `rev` and `snapshot`, and only while WatchConnectivity reports a complication as enabled. It draws on a daily budget of about 50 transfers, so it is spaced 20 minutes apart, or 60 once 10 or fewer remain. A sync request wakes the iPhone app in the background; the watch sends one when it has no connection, after a wrong-secret error, or on Try Again. An older watch ignores `prefs`, and a new watch paired with an older phone keeps the defaults.

## Behaviour changes from the first version

Bringing the app to desktop parity changed some things that users of the first version will notice:

- **Numbers.** Western compact numbers are "1.2M" (one decimal), not "1.23M", and there is no "T" (a trillion reads `1000B`). The decimal separator is always ".", and full counts use en-US grouping in every locale. Costs use the desktop's format: the symbol directly before the amount, no grouping, `$0.4200` below $10 and `$1234.50` from $10 up, with `NT$`, `HK$` and `¥` for the other display currencies. Provider balances keep their own currency and use `$` and `¥`, otherwise `CODE 12.00`.
- **Limits.** Meters use the provider's colour at the window's tone opacity instead of green, amber and red (the watch complications, which lead with the tightest window, keep green, amber and red for how much is left). Status chips use the desktop's Settings-tag wording on every surface, which replaces the macOS-widget wording ("Available", "Rate limited"). Account emails show unmasked in the app by default, as on the desktop (`maskLimitAccountEmails` is off; there is a toggle), while the snapshot, the widgets, the watch and WatchConnectivity keep them masked.
- **Overview.** The default modules follow the desktop: Tools and Devices are hidden, Limits, Models, Sessions and Activity are shown, plus the iOS-only Token components. The original "Daily trend" card is replaced by the Activity module and the Trends screen.
- **Snapshot order.** The snapshot's Limits follow the provider order (catalog order by default) instead of "ready first". The Limits widget's automatic list is still most-constrained-first, unless a Home provider order is set, and it now drops the hidden Home providers.
- **Refresh.** Every refresh interval is now a setting. The defaults (Live, 15 minutes for widgets, 1 minute for the watch, 20 for complications) reproduce the original timings.

Where iOS deliberately differs from the desktop: a device scope exists (the desktop has none) and follows the Hub's aggregate expiry rules; chart ranges are N calendar days ending today with gaps filled with zeros, not the last N rows of a History that omits idle days; fixed ranges for the aggregate merge `/api/history` with the aggregate's live today under the phone's day, where the desktop merges per-device histories under per-device day keys, so they differ only for fleets spanning time zones; the Activity grid is Sunday-first whatever the locale; the Overview Tools module honours hide, pin and order (the desktop's Home module ignores them); and the Trends screen's mode, range, stack and metric are remembered per device in `@AppStorage` (`trends.*`), like the desktop's in-memory choice, not in `DisplayPreferences`.

## Not in the app

- Light theme, theme presets and theme codes: the Home Screen surfaces are designed dark-first, and widgets force a dark scheme.
- The Codex reset forecast, a third-party service the desktop offers opt-in.
- Binding a subscription to an account (plan-label tooltip, value multiple): it needs the account key, which the Kit deliberately drops, and a write UI. The top-up projection uses the binding's email or the provider's only account.
- Device deletion and every other write: the app is read-only. Notifications: the Hub has no push channel.
- Collection, tray, window, Edge Dock, bubble, Discord, startup, updates and WSL status: they do not apply to a phone.
- Hub "update available" beyond the legacy case: the Hub screen shows the runtime and the `hubBuild` core and runtime revisions, or "Legacy Hub" with a redeploy hint when the Hub reports no `hubBuild`. It does not compare the revisions with the desktop's `src/shared/hubBuildRegistry.json`, because mirroring that file in Swift would make every `npm run update:hub-build` leave a second generated file stale, so an out-of-date Hub that does report `hubBuild` is not flagged.
- Session transcripts and exchanges, the all-time session list and Reasonix native sessions: they live in local files, not on the Hub (the session detail says so).
- "No synced data" placeholder rows for providers that are enabled on a computer but have not reported: they need the collection-side enabled-provider set.
- The desktop's per-provider account-title heuristics and bespoke provider layouts beyond the generic windows, with a few exceptions such as MiMo's product in the title and Antigravity's verification notice.
- The dashboard flat style, and `viewDisplayOrder` / `hiddenViews` beyond the Status tab: the tab model differs.
- Fixed ranges (Week, 7D, 30D) in widgets, the watch and complications: they offer today, month and all time only, as the macOS widget does, and their snapshot holds no per-tool History.

## Compatibility surfaces and gotchas

- **Never rename a widget or complication `kind`.** WidgetKit identifies placed widgets and watch-face complications by it, so a rename removes them from users' Home Screens, Lock Screens and watch faces. The kinds are `TokenMonitorUsageWidget`, `TokenMonitorLimitsWidget` and `TokenMonitorActivityWidget` (`WidgetKind` in `TokenMonitorWidget/WidgetSupport.swift`; the last one is `ActivitySnapshot.widgetKind` in the Kit, because the app reloads that widget by kind), and `com.tokenmonitor.watch.usage` and `com.tokenmonitor.watch.quota` (`ComplicationKind` in `TokenMonitorWatchWidget/ComplicationTimeline.swift`). The configuration intents' parameter names (`period`, `breakdown`, `provider`, `metric`) and their choices' raw values are part of a placed widget's stored configuration, so treat them the same way.
- **Shared files and keys are a contract between builds.** The App Group files `token-snapshot.json`, `activity.json` and `model-aliases.json` (in `Library/Caches/TokenMonitor/`), the defaults keys `displayPreferences.v1`, `exchangeRates.v1` and `hubBaseURL`, and the Keychain item are read by the app, the extensions and the watch, which can be different builds. Add fields as optional; do not rename or reinterpret one. `DisplayPreferences` is stored and sent to the watch as JSON and decoded leniently, so a new key needs only a default; never rename or repurpose an existing one.
- **Deep links.** `tokenmonitor://` is registered in the app's Info.plist and parsed by `DeepLink` in the app target: `dashboard` (also `overview`, or no route) with an optional `period=today|month|week|last7|last30|allTime`, `trends`, `limits`, `devices`, `settings`, and `status` (the Status tab, or the service-status screen in Settings while the tab is hidden). The widgets link with `dashboard?period=today|month|allTime`, `limits`, `settings` and `trends` (the Activity widget). The scheme is open to anything that can open a URL, so add routes and keep the existing ones working.
- **The WatchConnectivity payload is a contract between phone and watch builds** that can differ in the field. The keys are mirrored in `PhoneSessionBridge.Key` and `WatchSessionBridge.Key` (`prefs` is `PreferencesPayload.contextKey` in both); change both together. The watch ignores, without any error, a payload whose `v` is not exactly its own `protocolVersion`, so bumping it silently stops an older counterpart from syncing; plan the transition before changing a key's meaning. `prefs` was added without a bump: an older watch ignores it and a newer one without it keeps the defaults.
- **`TokenSnapshot` and `ActivitySnapshot` changes.** Adding a field is safe. Changing a field's meaning needs a `currentSchemaVersion` bump, after which readers ignore newer files instead of misrendering them. Keep the encoded sizes within their budgets (snapshot 16 KB, activity 12 KB, preferences payload 8 KB), which tests pin or the encoders enforce.
- **Widgets, the watch and complications never decode History, sessions or projects.** That is how an extension exceeds its memory limit. Anything they need from them is written by the app as a small App Group file, as `activity.json` is, and extensions decode `/api/stats` with `.compact` or `.compact(scopedTo:)`.
- **`Int` is 32-bit on Apple Watch hardware** (arm64_32; the watch simulators and the Linux tests are 64-bit). Token counts the watch and the complications decode clamp at 2,147,483,647, so add them with the Kit's saturating sums (`PeriodSummary.tokens(notIn:)` for an "Other" row) rather than `+`, and no integer literal above that may appear in code the watch compiles (its two targets, `TokenMonitorKit` and `TokenMonitorUI`); type a wider constant as `Int64` or `Double`. CI's watchOS device build (`generic/platform=watchOS`) catches such literals.
- **The secret lives in the Keychain on both devices** (`kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`: readable after the first unlock, never iCloud-synchronized or restored from a backup to another device; saving moves an item written by an earlier build to that class). WatchConnectivity also retains the last application context, which includes the secret, inside each app's sandbox, and the watch reapplies the retained context at activation. The encoded `HubConnection` (secret included) belongs only on that transfer. Before the first unlock the Keychain refuses reads, so widgets and the watch keep showing the cache and never call the Hub without its secret.
- **ATS is `NSAllowsArbitraryLoads` only**, in all four Info.plists, because users run plain-HTTP Hubs on a LAN or tailnet. Do not add `NSAllowsLocalNetworking`: iOS then ignores `NSAllowsArbitraryLoads`, which those plain-HTTP Hubs rely on.
- **`INFOPLIST_KEY_NSLocalNetworkUsageDescription` in `project.pbxproj`** (Debug and Release) and the English text in `TokenMonitor/InfoPlist.xcstrings` must stay in step.
- **Generated asset symbols are on.** Each target's `AccentColor` (and the widget targets' `WidgetBackground`) color set generates `Color.accent` (and `Color.widgetBackground`), so do not declare same-named `Color` statics in target code or `TokenMonitorUI` (`TMTheme.accent` is fine: it is namespaced). The vendor icons generate `vendor…` image symbols, which collide with nothing.
- **The vendor catalog and icons are generated; never edit them by hand.** `VendorCatalog+Generated.swift` and the three `VendorIcons.xcassets` catalogs (in `TokenMonitor/`, `TokenMonitorWidget/` and `TokenMonitorWatch/`; the complications draw no marks) are rendered by `scripts/sync-ios-vendors.js` from the desktop's `vendorPresentation.js`, `clientCatalog.js`, `limits/providers.js`, `modelVendorFor()` in `usageCharts.js`, the `.row-icon-*` mask rules in `styles.css` and the artwork in `assets/icons/`. After changing any of them run `npm run sync:ios-vendors`; `npm run sync:ios-vendors -- --check` and `tests/shared/iosVendorCatalog.test.js` (part of `npm test`) fail on drift, and `VendorIconTests` checks that every asset name the Kit returns exists in all three catalogs. The icons are template images tinted by the app and loaded by name (`vendor-<stem>`, through `VendorCatalog.iconAssetName(for:context:)`; the `.limits` context applies the Limits page's artwork overrides) and fitted into a square frame by `VendorMark`, because the artwork is not all square. The generator sanitizes each SVG deterministically so Xcode's renderer draws the same silhouette the desktop masks rows with, and refuses artwork it cannot keep faithful (`<text>`, `<image>`, unknown style properties). `token-monitor.svg` is a `<text>` glyph, so the app uses the SF Symbol `sum` for it.
- **The stream client omits `x-token-monitor-stream: 2`** on purpose: with it the Hub sends `freshness` deltas that must be merged into a held snapshot, while without it every update is a complete `stats` event.
- **WidgetKit and watch refresh intervals are requests, not guarantees.** The system budgets reloads, so a widget can lag well behind its ask; the stale thresholds sit at twice the interval for that reason.

## Localization

String Catalogs (`Localizable.xcstrings`) sit in each target folder, with `InfoPlist.xcstrings` in the iPhone app for the Local Network prompt. The source language is English, with `ja`, `ko`, `pt-BR`, `zh-Hans` and `zh-Hant` translations, and every user-facing string needs all of them. `TokenMonitorKit` and `TokenMonitorUI` contain no user-facing strings: the Kit returns enums, numbers and structured labels (such as `LimitStatusLabel`) and each target localizes them. Where the desktop has the text, the translation is the desktop's (`src/electron/renderer/i18n.js`; its `zh-CN` is `zh-Hans` and its `zh-TW` is `zh-Hant`), so wording matches across platforms; text the desktop has only in English is translated here in the same terminology. A catalog key is the English source text as Xcode extracts it, with interpolations as `%@`, `%lld` and `%lf` and positional forms (`%1$@`) whenever there are two or more. Product and vendor names are not translated.
